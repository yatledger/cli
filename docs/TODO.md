## 1. Коротко о проекте

**Что это.** `yat/cli` — браузерный PWA-кошелёк платформы **Ять (Yat)**. Ять — децентрализованная
система обмена ценностями на DAG и криптографии Ed25519 (см. `whitepaper-ru.md`). Этот репозиторий
— **только клиент**: он генерирует ключи у пользователя в браузере, подписывает транзакции, шифрует
сообщения и общается с сетью по GraphQL (чтение) и REST (запись). Ядро сети живёт в других
репозиториях.

**Для кого.** Для конечных пользователей сети Ять: владение ключами, переводы, приватные сообщения,
просмотр истории. Плюс это витрина проекта на этапе тестнета.

**Стек.** Vue 3 + Quasar 2 (Vite), Pinia, vue-router, vue-i18n; Apollo Client (GraphQL) и `ky`
(REST); IndexedDB (`idb`) для локального хранения; libsodium + tweetnacl + bip39/@scure +
@noble/hashes для криптографии. Весь код — JavaScript (TypeScript пока сознательно не используем).

**Зрелость.** **Ранний прототип / pre-alpha.** Есть рабочий вход/регистрация/восстановление,
безопасное (после правок) шифрование сида, отправка и чтение сообщений, базовый список транзакций.
Но при этом: половина страниц — заглушки, нет защиты маршрутов, отправка транзакций без валидации,
интерфейс местами черновой. До MVP не хватает бизнес-логики; до production — инфраструктуры и
полировки.

## 4. Задачи

### 🔴 P0 — Критично

---
**[T1]. Закрыть утечку сида и приватного ключа на странице профиля**
Характер: 🔴 Критично
Где: `src/pages/user/UserProfile.vue`
Проблема: страница `/profile` в открытом виде показывает **мнемоническую фразу** и **приватный
ключ** (первые 32 байта секретного ключа в base58). Любой, кто получил доступ к разблокированному
устройству или просто открыл эту страницу, может мгновенно скопировать ключи и увести все средства.
Более того, `const sk = base58.encode(user.sk.slice(0, 32))` вычисляется один раз в `setup` и не
обновляется — после входа на страницу при пустом сторе там окажется мусор/пустая строка.
Предложение: спрятать секреты за явное действие — кнопку «Показать» (а лучше — повторный ввод
пароля и/или подтверждение), добавить предупреждение о рисках, автозатемнение через N секунд,
запрет выделения. Показывать сид и ключ раздельно: «Резервная копия» и «Экспорт ключа». Само
значение читать реактивно (`computed`), а не в `setup`.
Ожидаемый эффект: секретные данные перестают светиться на экране «по умолчанию»; снижается риск
кражи при фишинге и демонстрации экрана.
Готово, когда: без явного подтверждения сид и приватный ключ не отображаются; есть предупреждение;
значения реактивны и корректны после входа.

**[T2]. Валидация и безопасность отправки транзакции**
Характер: 🔴 Критично
Где: `src/pages/SendTx.vue`
Проблема: сумма считается как `amount.value * 1000000` без проверок — принимает `NaN`, пустое
значение, `Infinity` и отрицательные числа; адрес получателя не проверяется вообще (можно отправить
на произвольную строку). Запрос `ky.get(... + 'pool')` стоит **вне** `try`, поэтому при недоступном
бэкенде получаем необработанное исключение. Подпись вычисляется дважды разными механизмами
(`signMessage` из libsodium и `sign` из tweetnacl), есть блок мёртвого кода, куча `console.log`.
Кроме того `msg.value` **перезаписывается** зашифрованным текстом, портя исходное поле ввода.
Предложение: вынести логику в отдельный модуль (например `src/services/tx.js`); валидировать сумму
(конечное положительное число, ограничение точности до 6 знаков), адрес (длина/декодируемость
base58), обязательность полей; обернуть сетевые вызовы в `try/catch` с понятными ошибками; оставить
**один** способ подписи; показывать диалог подтверждения с суммой, получателем и «итого»; не мутировать
`ref` с сообщением.
Ожидаемый эффект: невозможно случайно подписать/отправить некорректную или пустую транзакцию; сеть
больше не «роняет» приложение молчаливым исключением.
Готово, когда: форма не отправляется при невалидных данных и явно объясняет почему; ошибки сети
показаны пользователю; подтверждение есть перед отправкой.

**[T3]. Защитить маршруты, требующие кошелька**
Характер: 🔴 Критично
Где: `src/router/routes.js`, `src/layouts/MainLayout.vue`
Проблема: все маршруты доступны всегда. Страницы `/send`, `/msg`, `/tx`, `/profile`, `/global`
не проверяют, разблокирован ли кошелёк. При пустом сторе они показывают бессмысленные данные, а
`/profile` (см. T1) — вообще потенциальную утечку. Логика «выйти на /login» размазана в
`watch(noLogin)` внутри layout и срабатывает только при смене значения, а не при прямом заходе по
URL.
Предложение: ввести глобальный navigation guard (`router.beforeEach`) с метаданными маршрута
`meta: { requiresWallet: true }`. Незалогиненного — редиректить на `/login`, сохраняя `redirect`.
Убрать побочную навигацию из `watch` в layout.
Ожидаемый эффект: предсказуемое поведение при любом способе попадания на страницу; закрыт доступ к
секретам и «полурабочим» экранам до входа.
Готово, когда: прямой заход на защищённый URL без входа ведёт на `/login`; после входа возвращает
на исходную страницу.

**[T4]. Безопасное управление сессией: блокировка и выход**
Характер: 🔴 Критично
Где: `src/layouts/MainLayout.vue`, `src/stores/user.js`
Проблема: `exit()` очищает только сигнатуру/pk/seed, но `user.crypt` остаётся `true`; в `clear()`
порядок операций запутан (`reset()`, затем `crypt = false`, затем `location.reload`). Нет
автоблокировки по бездействию и при уходе со страницы — кошелёк остаётся разблокированным в фоне.
Секретный ключ живёт в памяти неограниченно долго.
Предложение: ввести `lock()` и `unlock()` в сторе как симметричные операции; опциональная
авто-блокировка по таймауту бездействия и по `visibilitychange`; на выход явно стирать ключевой
материал (`sodium.memzero` для буферов, где возможно). Привести `clear()` к читаемому порядку.
Ожидаемый эффект: кошелёк не остаётся разблокированным без присмотра; выход гарантированно
«очищает» память.
Готово, когда: выход/блокировка переводят UI в состояние «требуется пароль»; ключи не
восстанавливаются без ввода пароля.

**[T5]. Реактивность данных после входа (баланс, транзакции)**
Характер: 🔴 Критично (для функциональности кошелька)
Где: `src/pages/user/UserTx.vue` (реальная проблема), `src/pages/IndexPage.vue` (частично)
Проблема: в `UserTx.vue` запрос строится как `useQuery(gql, { addr: user.pk })` — здесь `user.pk`
читается **один раз** в момент `setup` и попадает в `variables` как **статический снимок**. Если
страница открыта до разблокировки кошелька (или адрес появился позже), запрос уходит с пустым
адресом и **никогда не перезапрашивается** — история пуста до перезагрузки. В `IndexPage.vue`
ситуация лучше: в `variables` и `enabled` передаётся реактивный `computed(() => user.pk)`, что
Apollo умеет отслеживать, — там проблема в основном в использовании `enabled` как строкового
условия (пустая строка = выключено) и в отсутствии обработки состояний (см. T6).
Предложение: в `UserTx` передавать реактивные `variables` (`() => ({ addr: user.pk })` или
`computed`) и реактивный `enabled`, чтобы Apollo перезапрашивал при появлении адреса; при желании
дожидаться `user.ready` перед запросами.
Ожидаемый эффект: после входа история (и баланс) подгружаются сами, без перезагрузки страницы.
Готово, когда: вход в кошелёк на уже открытой странице приводит к загрузке данных.

Готово, когда: все три состояния визуально различимы; ошибка не выглядит как «нет данных».

**[T7]. Единая логика подписи и шифрования (устранение дублирования)**
Характер: 🟠 Важно
Где: `src/pages/SendTx.vue`, `src/boot/crypt.js`, `src/boot/crypt_.js`
Проблема: в `SendTx` одновременно используются libsodium-подпись и tweetnacl-подпись; есть
мёртвый закомментированный код; `uint8ArrayToHex(enc)` вызывается и результат выбрасывается. Рядом
лежит целый неиспользуемый модуль `crypt_.js` (tweetnacl-реализация). Два источника правды опасны
для криптографии — однажды подпишут не тем, чем проверяют.
Предложение: выбрать один крипто-стек (libsodium как основной — он уже в `boot/crypt.js`), удалить
`crypt_.js` и мёртвый код, оставить один `signTx`-путь. Канонизация транзакции (`orderedSum`) —
задокументировать как контракт протокола.
Ожидаемый эффект: меньше поверхностей для ошибок в критичном коде; единый формат подписи.
Готово, когда: подпись формируется ровно в одном месте; `crypt_.js` удалён.

## 5. Дизайн: отдельное видение

Раз уж речь о молодом продукте — вот цельное направление, к которому стоит стремиться. Не догма,
но рамка, чтобы разрозненные экраны сложились в узнаваемое приложение.

### 5.1 Идея

Ять — имя старой славянской буквы. Это редкий дар: у проекта уже есть **символ**, вокруг
которого можно построить всю айдентику. Предлагаю эстетику «**цифровой пергамент**»: серьёзный
финансовый инструмент, но с ощущением письменности и истории. Строгая сетка, много воздуха,
крупные числа, но тёплые материалы и каллиграфический акцент.

### 5.2 Палитра

Текущий `$primary: #311b92` (глубокий индиго) и `$dark-page: #110030` — хорошая основа. Дополнить:

- **Основа:** индиго (`#311b92`) → глубина `#110030`.
- **Акцент:** золото/латунь `#c9a227` — для денег, подписей, важных действий. Это «чернила» и
  «золотая печать» одновременно.
- **Фон-«пергамент»:** кремовый `#f6f1e7` для светлой темы (вместо чистого белого).
- **Семантика:** `positive` — зелёный, `negative` — терракотовый (мягче стандартного красного).
- **Тёмная тема:** индиго-ночь + золото; избегать «чистого чёрного».

### 5.3 Типографика

- **Заголовки:** гуманистическая антиква с характером (например, спектр `Spectral`/`Source Serif`)
  — отсылка к письменности. Крупные балансы и суммы — этим шрифтом.
- **Интерфейс:** чистый гротеск (Inter/Manrope) для читаемости.
- **Моноширинный:** для адресов, ключей, хешей — обязательно (сознательно избегать смешения в
  основном тексте).
- Убрать смешение Roboto Slab + Sofia Sans из компонентов, подключить один согласованный набор.

### 5.4 Экран за экраном (эскизно)

- **Онбординг:** полноэкранные шаги с крупной литерой **ѣ** как «печатью»; фраза — как рукопись
  на пергаменте, по 4 слова в строку с нумерацией; проверка — «вставь слово №7»; пароль — с
  индикатором-«печатью», которая «запечатывает» кошелёк.
- **Главный экран:** баланс-«номинал» крупной антиквой с валютой `$YAT`, ниже — QR-«паспорт» и
  две главные кнопки (Отправить/Получить). Ниже — последние операции лентой.
- **Отправка:** пошаговый «черновик → печать → отправка»: форма, затем карточка-квитанция с
  золотой печатью при подтверждении, затем результат с хешем.
- **История:** лента карточек, группировка по датам-«главам», входящие — зелёной стрелкой,
  исходящие — золотой. Зашифрованные сообщения открываются красивым «раскрытием письма».
- **Профиль:** «паспорт» (адрес, аватар-монограмма, QR) и отдельная «сейф»-секция для бэкапа.
- **Эксплорер (`/global`):** та же лента, но публичная; фильтры по сумме/времени/сообщениям.

### 5.5 Принципы UX

1. **Секреты — только по явному запросу** и всегда с предупреждением.
2. **Необратимое — подтверждать**, опасное — двойным подтверждением.
3. **Одно главное действие на экран.**
4. **Никаких «пустых» состояний без объяснения** — везде спиннер/ошибка/пусто.
5. **Mobile-first**: нижняя навигация, крупные тапы, читаемые числа.
6. **Доступность:** контраст AA, фокус-рамки, `aria-label`, поддержка клавиатуры.
7. **Единые токены** вместо хардкодов стилей.

### 5.6 Движение

Сдержанно и по делу: skeleton при загрузке, мягкие переходы между шагами, «проявление» баланса,
лёгкая анимация копирования. Ничего, что мешает скорости.

### 6.3 Технические требования

- **Только JavaScript.** Без TypeScript, без unit-тестов, без комментариев в коде (правила
  проекта). Новый функционал сопровождается e2e-тестом.
- **Криптография** — исключительно через `src/services/wallet.js`; формат хранения
  `{ v, salt, nonce, ciphertext }` остаётся совместимым, изменения — через новую версию `v` с
  миграцией.
- **Секреты** (сид, приватный ключ) не отображаются без явного действия; никогда не попадают в
  cookie/localStorage/логи/сеть.
- **Маршруты**, требующие кошелька, помечаются `meta.requiresWallet` и закрываются гвардом.
- **Данные Apollo** привязываются к реактивному ключу адреса и перезапрашиваются при смене.
- **Отправка транзакции** проходит валидацию (сумма — конечное положительное число,
  адрес — валидный base58, поля обязательны) и подтверждение.
- **Ошибки** сети/крипто показываются пользователю через `Notify`, не «падают» в консоль.
- **Стиль** — по существующим конвенциям (2 пробела, без `;`, single quotes, `$t` для обеих
  локалей); `npm run lint` — 0 ошибок; `npm run test:e2e` — зелёный.
- **`libsodium-wrappers`** остаётся на `0.7.15`.

### 6.4 Definition of Done

1. Ни один секрет не виден без явного подтверждения; выход/блокировка возвращают состояние
   «нужен пароль».
2. Защищённый URL без входа ведёт на `/login` и после входа возвращает обратно.
3. Баланс и история подгружаются автоматически после входа, без перезагрузки.
4. Некорректная транзакция не отправляется; ошибка сети объяснена пользователю.
5. В консоли нет отладочных логов; мёртвый код удалён; `js-cookie` больше не зависимость.
6. Все пользовательские строки локализованы (en/ru); нет битых ссылок и маршрутов.
7. `npm run lint` — чисто; `npm run test:e2e` — проходит; новые потоки покрыты e2e.
8. README/AGENTS/скилл отражают фактическое состояние; CI (при внедрении) зелёный.
